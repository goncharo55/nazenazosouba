# なぜなぞ相場 — 日次マーケット概況の自動生成パイプライン

公開サイト: **https://goncharo55.github.io/nazenazosouba/** （GitHub Pages）

毎日 16:40 JST に実行する（日本の引け後。16:00 JST にGitHub Actionsが実データを置いたあと）。
米国は前営業日分（まだ確定していないため）、日本は当日分のデータを使う。特定銘柄の売買は推奨しない。
分からない値動きは「不明」でよい。

## いちばん大事なルール：数字は実データファイルから、WebSearchは「理由」だけ

過去、WebSearchのスニペットから数値を拾っていたため、指標カードの約2割が実データとズレていた
（2026-11 の監査：90記事・755指標点のうち153点が許容範囲外。11/9と11/10の日経平均は実際には
+2.33%・+2.87%の続伸なのに、どちらも古い値57,525.90円・-5.82%のまま掲載、など）。
別の月の記事・速報値と確定値の混在・数字の取り違えは、検索結果から数値を拾う方式では避けられない。
そこで **指数・為替・商品・暗号資産の値と、値上がり/値下がりランキングの騰落率は、必ず
`data/market_YYYY-MM-DD.json`（yfinance由来）の数字をそのまま使う**。WebSearchは、
「なぜ動いたか（材料・理由）」と「その日のニュース」を調べるためだけに使う。

## 全体の流れ（この順で実行する）

0. **リポジトリの取得**：クラウド実行の場合、まず https://github.com/goncharo55/nazenazosouba を
   clone（またはpull）する。このリポジトリが `data/archive.db` を含む唯一の永続化先。
   作業はこのリポジトリのルート（＝このREADMEがあるディレクトリ）で行う。
   `db.py` / `render.py` / `build_site.py` は標準ライブラリのみで動く。`verify_edition.py`
   （手順2.6）だけは pandas / yfinance をimportするので、最初に
   `pip install -r requirements-market.txt` を実行しておく（pypi.org は到達可能）。

   **⚠ ネットワーク制約（重要・実測済み）**：このクラウドサンドボックスは、外部ネットワークアクセスが
   ごく一部のドメインに限定されている（実測：`github.com` と `pypi.org` は到達可能、
   `finance.yahoo.com` / `fred.stlouisfed.org` / `stooq.com` / `google.com` 等はBashからのcurlも
   WebFetchも403でブロックされる。2026-08-19に確認）。だからこのサンドボックスの中では
   `fetch_market_data.py`（yfinance）は動かない。代わりに **GitHub Actions
   （`.github/workflows/market-data.yml`）が毎日16:00 JSTに実データを取得して
   `data/market_YYYY-MM-DD.json` をコミット**してくれている。ルーティンはそれを `git pull` で受け取る。

1. **実データファイルを受け取る**
   - `git pull origin main` して、今日（JST）の `data/market_YYYY-MM-DD.json` があるか確認する。
     まだ無ければ（Actionsの遅延は数十分あり得る）、**1分おきに `git pull` しながら最大15分待つ**。
   - 15分待っても無い場合のフォールバック：WebSearchで数値を調べて記事を書いてよいが、
     数字は概数で書き、`sources_note` に「実データ取得に失敗したため速報ベースの概算を含みます」と明記し、
     指標カードの `asof` に「（概算）」を付ける。また `PushNotification` でユーザーに
     「market dataが生成されていないのでActionsを確認してください」と通知する。
   - ファイルの中身：
     - `indices`：edition JSON の `indices` にそのまま使える12指標（value_text/unit/asof/delta/pct）。
       日付の揃え方は固定（日本の指標＝当日の東証引け、米国の指標＝直近のNY引け、24時間資産＝最終日足）。
       `streak.phrase`（「4日続伸」「3日ぶり反落」など）と `is_1y_high` / `is_1y_low` も入っている。
     - `movers.JP` / `movers.US`：日経225・S&P500の値上がり/値下がり上位（騰落率は実データ）。
       **記事化する個別銘柄は、ここに載っているものから選ぶ**（目安：各市場4〜9銘柄。値動きの大きさ・
       話題性・同じテーマで動いているかで選ぶ）。`pct` はこの値をそのまま使う。
     - `sessions`：`jp` / `us` は各市場の最終セッション日、`jp_open_on_target` が false なら
       東証は対象日が休場（日本の個別銘柄セクションは書かない。24時間資産や前営業日のデータで補う）。
       `movers.JP` が空の日も同様。
   - **見出し・本文の「続伸」「続落」「ぶり反発」「最高値更新」などの表現は、`streak` と
     `is_1y_high/low` だけを根拠にする。** 自分で数えたり、記事から推測しない。
   - **動きが小さい資産を無理に取り上げるくらいなら「今日は目立った動きはなかった」と書いてよいが、
     記事全体がスカスカにならないよう、必ずどこかの市場・資産に材料を見つけること。**

2. **値動きの理由を調べる**（WebSearchツール。ここで初めてWebSearchを使う）
   - 記事化する各銘柄・指数について `"<銘柄名> 株価 <理由 or 急落/急騰> <日付>"` のようなクエリで
     WebSearchし、**理由・材料だけ**を拾う（そこに出てくる数字は使わない）。
   - 明確な材料が見つからない場合は無理に理由を作らない。
     `reason` には「明確な材料は確認できず」「〇〇株全体の値動きに連れ安（連れ高）」のように正直に書く。
   - 複数銘柄が同じ理由（例：金利上昇、AI相場の調整、決算シーズン）で動いている場合は、
     その「共通テーマ」を記事の見出し・3行まとめ・きょうの用語解説のネタにする（読み応えが出る）。
   - 検索は目安30件以内・5〜10分で切り上げる（数字を探し回る必要が無くなったので、以前より短くて済む）。

2.5. **本文に書く「それ以外の数字」の裏取り（過去に事故った箇所）**
   - 事故例：**2026-08-26分で、アドバンテストの上昇率を実際は+3.63%だったのに+16%台と書いた。**
     検索で拾った別の月（7月の決算時）の記事を当日のものと取り違えたのが原因。
   - 指標・騰落率は上記の実データを使うので、ここで気をつけるのは決算数値・目標株価・先物の水準・
     出来高など `market_*.json` に無い数字。これらは、(1) 検索結果に**日付が明記されていて対象日と
     一致する**ものだけを根拠にし、(2) **1日の値動きが±8%を超える**ような特別な主張は別クエリで
     必ず裏取りし、(3) 結果が食い違うときは都合の良い方だけを採用せず、書かない（または
     「明確な材料は確認できず」にする）。
   - 本文に日経平均の水準を書くときは、`market_*.json` の `indices` の終値と一致させる
     （前引け・高値・安値に言及する場合は、それと分かる書き方にする）。

   - **重大ニュース（CEO・経営陣の交代、不祥事、M&A、破綻、当局の処分など）を書く／あるいは公開済みの記事の記述を「誤りだった」と直すときは、必ず一次情報（会社の公式発表・IR、SECの8-K、東証の適時開示）か、大手報道（日経・ロイター・ブルームバーグ・NHK・NPR・WSJ 等）の2社以上で確認する。** 日本語と英語の両方で、会社名＋出来事のクエリを試すこと。**「検索で見つからなかった」は、出来事が無かった根拠にならない**（検索結果が薄いだけのことが多い）。事故例：2026-11-16に、事実だった「エヌビディアのフアンCEOが辞任（11/12発表、SEC 8-Kで確認）」を、検索結果が薄かったために「社内調査の段階で辞任は未発表」と誤って書き換えてしまった。確認できなければ、既存の記述を勝手に消さず、「報道によると」と留めるか、PushNotificationで人間に確認を求める。
2.6. **検証（必須）**：edition JSON を作ったら、DBに保存する前に必ず実行する。
   ```
   python verify_edition.py data/edition_YYYY-MM-DD.json --fix
   ```
   - `--fix` は `indices` を実データで置き換え、個別銘柄の騰落率を実データに合わせ、本文の
     「N日続伸/続落」を（向きが同じ場合に限り）正しい表現に直す。
   - それでも `ERROR:` が出たら、文章（見出し・3行まとめ・本文）を手で直して、`--fix` なしで
     もう一度 `python verify_edition.py ...` を実行し、**ERROR 0件になってから**手順4に進む。
     典型例：`[streak]`＝「4日続伸」と書いたが実データは「4日ぶり反落」（向きが逆なので、記事の筋書きごと
     見直す）、`[movers]`＝ランキング外の銘柄で±8%超の主張を実データで確認できない（外すこと）。
   - `WARN:` は目視で確認すればよい（前引けの水準に言及しているだけ、など）。

3. **記事データを組み立てる**：実データ（手順1）と理由（手順2）から edition dict を作り、
   `data/edition_YYYY-MM-DD.json` に保存する（`indices` は `market_*.json` からコピーする）。
   スキーマは下記「edition JSONの形」を参照。過去の `build_edition_20260819.py` は初回セットアップ時に
   手作業で作った例（現在の数値取得の仕組みとは別物）。

4. **DBに保存**：`python db.py save --json data/edition_YYYY-MM-DD.json`
   （SQLite: `data/archive.db`。同じ日付で再実行すると上書きされる）

5. **サイトを再生成**：`python build_site.py`
   - DBの全editionから `docs/` フォルダを丸ごと再生成する（Artifactツールは使わない）
   - `docs/index.html`（最新記事のミラー＝トップページ）、`docs/archive.html`（バックナンバー一覧）、
     `docs/glossary.html`（用語辞典）、`docs/editions/YYYY-MM-DD.html`（各日の固定リンク）を出力
   - URLの組み立ては `render.py` の `SITE_ROOT`（`/nazenazosouba`）を基準にした関数
     （`home_url()` / `archive_url()` / `glossary_url()` / `edition_url(date)`）が担当するので、
     手作業でリンクを書く必要はない
   - **公開は「pushするだけ」**：GitHub Pagesがリポジトリの `main` ブランチの `docs/` フォルダを
     配信するよう設定済みなので、以下の手順6でpushが通れば、数十秒〜数分で
     https://goncharo55.github.io/nazenazosouba/ に反映される。手動でpublishする操作は不要。

6. **用語辞典の更新（任意）**：その日の「きょうの用語解説」で新しい用語を扱った場合、
   `data/glossary_add_YYYY-MM-DD.json`（seed_glossary.jsonと同じ形式の配列）を作り、
   `python db.py add-glossary --json data/glossary_add_YYYY-MM-DD.json` で追加してから、
   もう一度 `python build_site.py` を実行する（`docs/glossary.html` に反映される）。
   既存の用語と同じtermは上書きされない（初出の説明を尊重する）ので、表現を変えたいだけなら
   このステップは不要。

7. **リポジトリへの保存＝公開**：作業後、必ず以下を実行する。
   ```
   git add -A
   git commit -m "YYYY-MM-DD分の記事を追加"
   git push
   ```
   これを忘れると、次回実行時に過去の記事やDBの内容が失われるだけでなく、**サイトも更新されない**
   （GitHub Pagesはpush済みの内容しか配信できないため）。

   **⚠ `git push` が失敗する場合**：2種類の失敗パターンが実測で確認されている。
   - `unable to access ... 403`（生の`git push`）：まず**GitHub連携のMCPツール**
     （`mcp__github__push_files` または `mcp__github__create_or_update_file`。ToolSearchで
     `select:mcp__github__push_files,mcp__github__create_or_update_file` を検索すると使える）
     を試す。`mcp__github__get_me` で認証中のGitHubユーザーを確認できる。
   - `mcp__github__push_files` でも `403 Resource not accessible by integration` になる場合：
     これは**このクラウド環境に接続されているGitHub連携（GitHub App）自体が、このリポジトリへの
     書き込み権限を持っていない**ことを意味する（2026-08-19に実測・確認済み）。README上の工夫では
     解決できない、claude.ai側の連携設定の問題。この場合は無理に何度も再試行せず、
     **PushNotificationツールでユーザーに「GitHub連携の書き込み権限を claude.ai の
     設定 → Connectors で確認してください」と通知した上で、生成済みファイルはローカルの
     working directoryに残したまま終了する**（次に人間が介入した際にpushできる状態にしておく）。

## edition JSONの形

```json
{
  "edition_date": "2026-08-19",
  "eyebrow": "Today's Market",
  "headline": "見出し（1行、その日のテーマを一言で）",
  "summary": ["3行まとめの1行目", "2行目", "3行目"],
  "tags": ["#タグ1", "#タグ2"],
  "indices": [
    {"ticker": "^GSPC", "name": "S&P500", "value_text": "7,691.76", "unit": "",
     "asof": "8/18 NY市場引け", "delta": -53.30, "pct": -0.69}
  ],
  "narrative": [
    {"flag": "JP", "title": "日本市場：...", "paragraphs": ["<p>の中身。<span class=\"num\">数字</span>のように強調可"]},
    {"flag": "US", "title": "米国市場（前日）：...", "paragraphs": ["..."]}
  ],
  "movers": [
    {"market": "JP", "ticker": "4385", "name": "メルカリ", "pct": 5.54, "kind": "equity", "reason": "..."}
  ],
  "lesson_title": "きょうの用語解説のタイトル",
  "lesson_body_paragraphs": ["段落1", "段落2"],
  "quiz": {
    "question": "一問一答のクイズ本文",
    "choices": [
      {"text": "選択肢1（正解）", "explanation": "この選択肢が実際に指している用語・概念の説明"},
      {"text": "選択肢2（誤答用のダミー）", "explanation": "これは別の用語○○の説明です、のように書く"},
      {"text": "選択肢3", "explanation": "..."},
      {"text": "選択肢4", "explanation": "..."}
    ],
    "answer_index": 0
  },
  "sources_note": "データ出典の一文",
  "generated_at": "2026-08-19 15:35 JST"
}
```

- `narrative` は配列なので、市場が休場の日は該当セクションを省いてよい。
  代わりに `flag: "24H"` などで為替・暗号資産のセクションを足してもよい。
- `movers` の `market` は `"JP"` / `"US"` / `"GLOBAL"`（24時間資産用）。
  `render.py` の `MARKET_LABELS` がパネルの見出しに変換する。
- `indices`（Market Snapshotのカード）は **12件** を目安に、以下の順で並べる
  （日本人読者向けサイトなので日本の指標を先頭に）：
  1. 日本 … 日経平均、TOPIX
  2. アメリカ … S&P500、Nasdaq総合、NYダウ
  3. ドル円
  4. VIX恐怖指数
  5. 米10年金利
  6. 金価格（NY金）
  7. SOX半導体指数
  8. 原油（WTI）、ビットコイン（枠を埋める24時間資産。休場日はここが特に効いてくる）
  - `unit` は数値の後ろに小さく添える単位（`"円"` `"%"` `"ドル"` など）。日経平均やTOPIX(ETF)・
    ドル円は `"円"`、金利は `"%"`、金・原油・ビットコインなど米ドル建て資産は `"ドル"`。
    S&P500・Nasdaq総合・NYダウ・SOX半導体指数・VIX恐怖指数のような無次元の指数値には
    実際の単位がないので、`unit: ""`（空文字、キー自体を省略してもよい）にして何も表示させない。
    「ポイント」などを書かない。
  - `asof` はその数値がいつ時点のものかを示す短いラベル（例: `"8/19 東証引け"` `"8/18 NY市場引け"`
    `"8/19 15:00"`）。日本市場の指標は当日の東証引け時点、米国株・VIX・金利は前営業日のNY市場引け
    時点、為替・金・原油・暗号資産のような24時間取引資産は記事執筆時点（`generated_at`と同じ頃）を
    想定。カードには「(前日)」のような曖昧な注記ではなく、この`asof`がそのまま小さく表示される。
  - 変化額(`delta`)の行には自動で「前日比」ラベルが付く。
- `tags` は記事上でクリック可能なハッシュタグとして表示され、クリックするとバックナンバー一覧
  （`archive.html?tag=...`）がそのタグの記事だけに絞り込まれた状態で開く（クライアントサイドJSのフィルタ、静的サイトのままでOK）。
- `quiz` は任意。省略すると記事に「きょうのなぞなぞクイズ」セクション自体が出ない。
  入れる場合は選択肢2〜4件、`answer_index` はその0始まりの正解位置。**選択肢を書く配列内での
  正解の位置は気にしなくてよい**（`render_quiz()`が`edition_date`をシードに決定的にシャッフルして
  表示するので、毎回先頭に書いても表示上は記事ごとにバラける。書く側が「正解を先頭に置きがち」に
  なる問題を仕組みで防ぐため）。
  その日の `lesson_title`（用語解説）の内容と対応する一問一答にすると、記事全体に一貫性が出て良い。
  各選択肢は `{"text","explanation"}` 形式にすること。正解でも誤答でも、選んだ選択肢の
  `explanation`（その選択肢が実際は何を指す言葉なのか）がその場で表示される。誤答を選んでも
  「はずれ」で終わらせず、その選択肢自体の学びになるようにするのが狙い。誤答は正解と紛らわしい
  別の実在する用語にすると（例: テーマ株 vs 新興株 vs 高配当株）、選択肢自体が副次的な用語解説になる。

## オリジナリティについて（重要）

このサイトは日経新聞などの記事の丸パクリ（要約・翻訳のみ）ではない。以下を必ず守ること。

- WebSearchで得た情報は自分の言葉で書き直す。見出しやリード文をほぼそのまま言い換えただけの文章にしない。
- 単一の記事の視点をなぞるだけでなく、**複数の値動き・複数日のデータを横断して関連付ける**ことを
  「なぜなぞ相場」らしい付加価値にする。例：
  - 前日の米国の値動きと当日の日本の値動きを因果でつなぐ（例：米SOX急落→翌日の日本の半導体・AI関連株安）
  - 一見バラバラな複数の値上がり/値下がり銘柄に共通するテーマを見つけて言語化する
    （例：電線株3社＋ソフトバンクGが同時に売られた→「AIテーマ株」という共通項でくくる）
  - 指標同士の関係を説明する（金利と成長株、VIXと株価、出来高と値動きの信頼度、など）
- 事実（何が何%動いたか）はどの情報源を見ても同じだが、「どの事実を選び、どうつなげて意味づけるか」に
  このサイトの視点を出す。きょうの用語解説は、その日の値動きから逆算して「今日はこれを説明すると
  読者の理解が深まる」というテーマを選ぶこと（前もって決まった辞書的な項目を順番に消化するのではない）。
- 出典は `sources_note` に明記し、特定の記事の丸写しではなく参照であることを示す。

## 文章のスタイルについて（「AIっぽさ」を消す）

収益化・SEOを見据えており、機械的なAI生成記事に見えないことが重要。以下を意識して書くこと。

- **同じ言い回しを繰り返さない**。「〜とみられる」「背景には〜があります」「一方で〜」を毎段落で
  使わない。1つの記事の中でも文末表現・接続語にバリエーションを持たせる。
- **常に両論併記・バランス型にしない**。「〜という見方がある一方、〜という指摘もある」を機械的に
  繰り返すと没個性になる。今日の値動きに対して踏み込んだ一言（「〇〇の下げはやりすぎに見える」等）を
  入れてもよい。ただし投資助言にならない範囲で（事実の評価・解説であって、売買推奨ではないこと）。
- **箇条書きに逃げない**。本文（narrative）は基本的に地の文で書き、リズムのある文章にする。
  短い文と長い文を混ぜる。
- **具体的な数字・固有名詞を先に出す**。「〜という報道がありました」で終わらせず、
  「日経新聞によると〜」のように主語を明確にする。
- 1記事につき最低1つは、その日ならではの「へぇ」ポイント（複数銘柄を貫く共通テーマ、
  意外な連動、過去の類似局面との比較など）を作る。これが「なぜなぞ相場」らしさになる。
